# 무신사 의류 랭킹 일일 리포트

## 목표
매일 오전 6시(KST), 무신사 의류 전체 랭킹(일간·주간·월간)을 수집해 남성/여성별로 잘 팔리는·뜨는 아이템, 핏, 실루엣,
소재, 컬러를 분석하고 추천 아이템을 뽑는다. 결과는 기간마다 **고정 주소 하나**(GitHub Pages `docs/`, `docs/weekly/`,
`docs/monthly/`)에 날짜별로 쌓는다. 매일 새 링크를 보내지 않는다.

## 수집 범위 (2026-09-25부터)
- 랭킹: **남성·여성 전체 랭킹**(섹션 199, 카테고리 000), 기간 `period=DAILY`·`WEEKLY`·`MONTHLY` (`common.PERIODS`)
- 1위부터 한 페이지(≈100위)씩 내려가며 **의류만 골라 성별마다 300개**가 모이면 멈춤 (2026-09-25 사장님 결정: "전체 랭킹 300위, 의류만, 300개 채우기")
- 의류 = 무신사 대분류 상의 001, 아우터 002, 바지 003, 원피스/스커트 100
- 제외: 뷰티 104, 신발 103, 가방 004, 모자 120, 소품 101, 속옷/홈웨어 026, 디지털/라이프 102, 키즈 106, 스포츠/레저 017(운동복 포함)
- 전체 랭킹에는 카테고리 표시가 없어서(모두 000) **상품 상세정보의 대분류로 의류인지 판별**. 비의류는 요청 1번, 의류는 2번(소재 포함). 한 번 본 상품은 다시 요청 안 함
- 급상승(201)·NEW(200)·유니섹스 구분은 쓰지 않음 (2026-09-24 사장님 결정)
- CSV의 `rank` = 무신사 전체 순위(비의류 포함), `clothing_rank` = 의류끼리 순위(1~300, 분석 가중치에 사용)
- 2026-09-24 기록은 예전 방식(카테고리별 1~200위)이라 추세 비교에서 자동으로 빠짐 (`analyze_trends.data_scope`)

## 순서와 Tool
| 단계 | Tool | 결과물 |
|---|---|---|
| 1. 랭킹 수집 (의류 판별용 상세정보 포함, 기간마다) | `tools/musinsa_fetch.py --period` | 일간 `data/history/`, 주간 `data/history_weekly/`, 월간 `data/history_monthly/` 아래 `YYYY-MM-DD.csv` |
| 2. 빠진 상세정보 채우기 | `tools/product_details.py` | `data/product_details.json` (상품별 누적 저장소) |
| 2-2. 후기 요약 (카테고리별 인기 TOP 50, 7일에 한 번, 하루 최대 120개) | `tools/review_summary.py` | `data/review_summaries.json` |
| 3. 분석 | `tools/analyze_trends.py --period` (분류: `tools/classify_attributes.py` + `tools/attribute_keywords.json`) | `.tmp/analysis_YYYY-MM-DD.json` (주간·월간은 `analysis_weekly_…`) |
| 4. 리포트 | `tools/build_report.py --period` | `docs/`(일간), `docs/weekly/`, `docs/monthly/` 각각 `index.html`(최신)·`reports/날짜.html`·`dates.json` |

- 상품 상세정보·사진 판독·후기 요약은 상품 단위라 세 기간이 같이 씀 (같은 상품을 두 번 받지 않음).
- 리포트 맨 위 [일간|주간|월간] 전환은 보던 성별·탭을 유지한 채 이동.

한 번에 실행: `python tools/run_daily.py` (수집 셋 다 → 오늘 리포트 날인 기간만 리포트). 재확인: `--only-missing`. 리포트 날이 아닌데 만들 때: `--report weekly`
자동 실행: `.github/workflows/daily.yml` (GitHub Actions, UTC 21:00 본 실행 + UTC 03:00·11:00 재확인, 제한 300분). 실패하면 GitHub이 저장소 주인 계정 이메일로 자동 알림.
(`tools/send_email.py` + `--alert-on-fail`은 PC에서 돌릴 때 Gmail로 알림을 받고 싶을 때만 사용 — 현재 미사용)
사진을 품은 한 장짜리 페이지(Claude 링크 등): `python tools/build_report.py --date 날짜 --standalone 파일.html`

## 리포트 구성 (2026-09-25 개편: 패션 디자이너 실무용, 목적별 탭 + 남성·여성 전환)
맨 위 [남성 | 여성] 전환은 탭을 바꿔도 유지. 주소 끝 `#여성-소재컬러`처럼 성별-탭으로 특정 화면 공유 가능, 마지막 화면은 브라우저가 기억.
| 탭 (주소 이름) | 디자이너 용도 | 내용 |
|---|---|---|
| 1 오늘 요약 (`요약`) | 흐름 파악·회의 공유 | 자동 요약 문장(인기 아이템, 1위 아이템 특징, 오른 아이템, 컬러, 원단, 가격) + 핵심 지표 카드 + 카테고리 구성 |
| 2 카테고리별 인기 TOP (`인기`) | 잘 팔리는 상품 보기 | 상의/아우터/바지 버튼, 사진 카드 20개 + '더보기'로 50위까지. TOP 50 카드 전부(더보기 포함) 아래 후기 요약(좋아요, 아쉬워요, 대표 후기. 설문·후기 수·3점 이하 비율은 사장님 결정으로 화면에서 뺌) |
| 3 카테고리 순위 (`기획`) | 아이템 기획 | 아이템 순위표(인기 비중·어제 대비·상품 수·중간 가격·최고 순위, 0.5%p 이상 오른 줄 초록) + 추천 아이템 5개 |
| 4 디자인 참고 (`디자인`) | 아이템별 스펙 | 카테고리 버튼 → 아이템 카드(잘 팔리는 사진 6장, 실루엣·기장(팬츠류만) / 원단 / 핏 / 소재 / 컬러 / 디테일) + 대분류(아우터/상의/하의)별 핏·실루엣·디테일 순위 |
| 5 소재·컬러 (`소재컬러`) | 원단 소싱·컬러 기획 | 대분류(아우터/상의/하의)별 컬러 팔레트 + 원단·소재 순위 (두께는 뺌) |
| 6 가격 (`가격`) | 가격 포지셔닝 | 아이템별 실판매가(중간)·정가(중간)·평균 할인율·주로 팔리는 실판매가(가운데 50%) 막대 + 가격대 분포 |
| 7 시장 동향 (`동향`) | 경쟁 상품 모니터링 | 순위 급상승 + 새로 TOP 50 진입 |

- 대분류 하의 = 바지 + 스커트 (원피스는 대분류 집계에서 뺌). 2026-09-25 사장님 요청으로 탭 순서·이름 변경, TOP 20+더보기 50, 대분류별 분류, 정가 추가.
- 용어: '순위 가중 비중' 대신 **인기 비중**(순위가 높을수록 크게 반영)으로 통일.
- 아이템 종류별 정리의 실루엣·기장은 팬츠류만, 핏은 유지 (2026-09-25 사장님 결정).
- 화면 점검: Edge 헤드리스로 캡처 (`msedge --headless=new --screenshot=파일 --window-size=1280,1800 "file:///…/docs/index.html#남성-가격"`). 휴대폰 폭은 창을 좁히면 잘못 찍히니 390px 너비 iframe 안에 넣고 찍기.
- CSS 이름 주의: `.bar`는 막대 그래프 이름. 새 부품에 같은 이름을 쓰면 화면이 깨짐(2026-09-25 상단 메뉴가 제목 위에 겹친 일).

- 후기 목록: `https://goods.musinsa.com/api2/review/v1/view/list?goodsNo={번호}&selectedSimilarNo={번호}&sort={정렬}&page={0부터}&pageSize=20&myFilter=false&hasPhoto=false&isExperience=false` (2026-09-25 추가, 사장님 승인. 정렬 `up_cnt_desc`=도움순, `goods_est_asc`=별점 낮은 순. pageSize 최대 20. 상품당 최대 6번, 7일에 한 번)
- 무신사 'AI 후기 요약' 문장 주소는 못 찾음(www.musinsa.com은 접속 안 함 원칙). 그래서 후기 원문을 받아 표현 사전(`review_summary.py`의 `REVIEW_PHRASES`)으로 셈. 빠지는 표현이 많으면 사전에 추가.
- 다섯 주소 모두 robots.txt 없음(404). www.musinsa.com은 등록 안 된 봇을 금지하므로 쓰지 않음.

## 수집 원칙 (바꾸지 말 것)
- 정직한 User-Agent(`MusinsaTrendReport/...`)로 요청. 사람 흉내·봇 위장 금지.
- 403/429(거부)가 오면 재시도하지 않고 멈춘 뒤 알림 메일. 사장님께 보고 후 방향 결정.
- 요청 횟수·간격을 늘리기 전에 사장님께 확인.
- 상세정보는 상품당 한 번만. 이미 있는 상품은 다시 요청하지 않음.

## 문제가 생겼을 때
- **"무신사가 데이터 요청을 거부"**: 클라우드(해외 서버)에서만 막히는지 로컬 PC에서 `python tools/musinsa_fetch.py`로 확인. PC에선 되면 Windows 작업 스케줄러로 전환 제안. 상세정보 단계에서 막혔다면 받은 만큼은 저장돼 있으니 다음 날 이어서 받음.
- **"수집 결과가 비정상적으로 적음" (구조 변경)**: `https://api.musinsa.com/api2/hm/web/v5/pans/ranking?storeCode=musinsa&subPan=product`에서 섹션 번호(`"sectionId"`)와 탭 이름(`applied_tab`, `extra_info`) 재확인. 상품 필드(`items[].info`, `items[].image.rank`)가 바뀌었으면 `parse_products` 수정.
